# 2026-02-07 — LLM-as-judge w E2E testach

## Problem

Happy-path test (`99-happy-path.spec.ts`) sprawdzał moduły shallow: "jest >0 kart, container widoczny". Nie weryfikował: ilości modułów, tytułów, otwarcia readera, ani — co kluczowe — **jakości wygenerowanego contentu**. Page object `PlanPage` miał metody `openModule()`, `getModuleTitles()` ale nikt ich nie używał.

Potrzebowaliśmy arbitra, który oceni czy LLM generuje sensowne lekcje, a nie bzdury.

## Rozwiązanie: LLM-as-judge

Utility `e2e/helpers/llm-judge.ts` — wywołuje tani model (Gemini 2.0 Flash przez OpenRouter) jako sędziego oceniającego content.

```
assertWithLlm({ content, criteria, threshold }) → { pass, score, reasoning }
```

- Score 0-100, threshold domyślnie 60 (w teście ustawiony na 50)
- Brak `OPENROUTER_API_KEY` = hard fail (nie skip — świadoma decyzja)
- Timeout 30s, content obcinany do 8000 chars
- Response parsowany z JSON (z obsługą markdown code fences)

## Rozszerzone asercje STEP 4

Po `waitForOutline()`:
1. `moduleCount >= 3` — prawdziwy plan ma minimum 3 moduły
2. Wszystkie tytuły niepuste
3. Otwórz pierwszy moduł → czekaj na "Ready" status (generowanie handbook)
4. `waitForHandbook()` — content stabilny (3 consecutive checks bez zmian)
5. `getHandbookText()` → minimum 100 chars
6. `assertWithLlm()` z kryterium: educational content, 200+ words, practical examples
7. `backToPlan()` — weryfikacja powrotu do grid

## Problemy napotkane po drodze

**Brak `data-testid="module-title"` w OutlineCard** — `getModuleTitles()` szukał selektora którego nie było w DOM. Dodane do `<h3>` w `OutlineCard.tsx`.

**`openModule()` klikał kartę zanim handbook się wygenerował** — karta jest klikalna dopiero przy `documentStatus === 'completed'` (tekst "Ready"). Dodany wait na `card.getByText('Ready')` z timeoutem `playbookGeneration`.

**`OPENROUTER_API_KEY` nie docierał do testów** — klucz był w Convex env (backend), ale Playwright worker go nie widział. Rozwiązanie: dotenv loading w `e2e/helpers/env.ts` + klucz w `.env.test`. Dodany import dotenv w `playwright.config.ts`.

**Sabotaż prompts.ts nie działał** — `renderPrompt()` ładuje z Langfuse first, fallback z pliku jest ostatnią deską. Sabotaż trzeba było wstrzyknąć bezpośrednio w `courseAi.ts` po `renderPrompt()` żeby nadpisać Langfuse response.

## Walidacja sabotażem

Trzy scenariusze testowane:

| Scenariusz | Score | Wynik |
|---|---|---|
| Normalny prompt | 70-75/100 | PASS |
| Sabotaż w `prompts.ts` fallback | 75/100 | PASS (Langfuse nadpisał!) |
| Sabotaż w `courseAi.ts` (lorem ipsum) | 10/100 | FAIL — "just placeholder text" |

Arbiter wychwycił lorem ipsum z reasoning: *"The content is just placeholder text (Lorem Ipsum) and does not cover the topic. It also lacks any educational value or practical examples."*

## Dodane pliki

- `e2e/helpers/env.ts` — dotenv loader + `getOpenRouterApiKey()`
- `e2e/helpers/llm-judge.ts` — `assertWithLlm()` utility
- `data-testid` na: `ReaderView.tsx`, `HandbookContent.tsx`, `OutlineCard.tsx`
- Nowe metody w `PlanPage`: `waitForHandbook()`, `getHandbookText()`, `getReaderModuleTitle()`

## Obserwacja: Langfuse jako zabezpieczenie

Ciekawy side-effect: Langfuse prompts nadpisują fallback z kodu. Sabotaż `prompts.ts` nie zadziałał bo Langfuse serwował oryginalny prompt. To jest de facto dodatkowa warstwa ochrony przed przypadkowym zepsuciem promptów przez commit — Langfuse jest source of truth na produkcji.

## Decyzje

- **Hard fail bez API key** zamiast graceful skip — testy muszą faktycznie testować. Skip daje fałszywe poczucie bezpieczeństwa.
- **Gemini Flash przez OpenRouter** zamiast tego samego modelu co generuje content — tani, szybki, wystarczający jako sędzia. Nie oceniamy poezji, oceniamy czy content nie jest lorem ipsum.
- **Threshold 50 (nie 60)** — LLM-generated content jest ok ale nie perfect. 50 łapie badziewie, nie blokuje "good enough".
