# 2026-05-23

## Pauza kampanii Google Ads — diagnoza i fix

Zespół zatrzymał kampanię Google Ads: 350 kliknięć, w GA "kilka" sesji, 0 transakcji. Wszedłem w to.

## Co znalazłem

Cztery problemy ułożone w łańcuch, każdy zjadał część ruchu zanim dotarł do następnego:

### 1. Redirect `/` → `/${lang}/` w `middleware.ts` był katastrofą

```ts
return Response.redirect(new URL(`/${lang}/`, url), 302);
```

`new URL('/pl/', url)` **dropuje query string**. Każdy Google Ads click trafiający na `/` tracił `gclid` + `utm_*` na pierwszym hopie. Atrybucja martwa.

Drugi tryb porażki: `parseLang` zwracał `'en'` / `'de'` jako default dla zagranicznego Accept-Language. Ale w `routes.ts` **nie ma `/en/` ani `/de/` jako route'ów**. Wszystko leciało do catch-all 404, gdzie ani GA4, ani PostHog, ani server-side beacon nie odpalały. Google'owe boty (`Google-Adwords-DisplayAds-WebRender`) wysyłają `Accept-Language: en-us` — wszystkie leciały na 404 i ginęły z analityki.

Rozwiązanie: skasować redirect w całości. Strona jest tylko po polsku, redirect był zbędny. Zachowałem `pl/*` → `pl-redirect.tsx` dla backward-compat ze starymi URL-ami w Google Index. Skasowałem 3 dead-code pliki (`language-redirect.tsx`, `lang-catchall.tsx`, `lang-layout.tsx`) niereferencowane od dawna.

### 2. Analytics summary kłamał — Top Paths nie szanował filtra

`summary` query w `convex/analytics.ts` nie przyjmował `pathPrefix`. UI w `AdminAnalytics.tsx` filtrował tylko tabelę szczegółów; karty (Total Views, Top Paths) pokazywały WSZYSTKO. Stąd absurd: filtr `pathPrefix=/problem/`, a Top Paths zawiera `/`, `/.env`, `/cennik`. Liczby kłamały o tym co liczą.

Dodałem `pathPrefix` do args + filtra. Karty i tabela teraz opisują tę samą skibę ruchu.

### 3. Bot pattern przepuszczał trzy kategorie szumu

UA-only detection w `BOT_PATTERN` przegapiał:

- **Skanery `.env`/`wp-admin`/`.git`/`adminer`** — udają normalny Chrome/Firefox, łapali się jako "human". 90%+ ruchu z US to byli oni.
- **Google ad render boty** (`Google-Adwords-DisplayAds-WebRender`, `Google-AdWords-Express`) — UA nie zawiera słowa "bot".
- **`CMS-Checker`, smoke-test** — same.

Dodałem `SCANNER_PATH_PATTERN` (path-based, dla `.env`/`wp-*`/`.git`/`adminer`) plus rozszerzyłem `BOT_PATTERN` o `adwords|googleads|cms-checker|smoke-test`. `recordPageView` flaguje teraz jako bot jeśli UA LUB path pasuje. Stare wiersze zostają jak były (bez backfillu).

### 4. **Najważniejsze:** Google Ads conversion tracking NIE ISTNIAŁ

Przeskanowałem cały kod: zero `AW-`, zero `gtag_report_conversion`, zero `gtag('event', 'purchase', ...)`. Stripe webhook flipa `paymentStatus = 'completed'` w bazie i koniec. Frontend (`BookProgressShell`) po redirectcie `?checkout=success` strzelał `payment_success` do PostHog i tyle.

**Google Ads nigdy w życiu nie widział żadnej transakcji** — bo nikt mu o niej nie mówił. To nie był "tracking problem", to był brak trackingu. Pauza kampanii była uzasadniona — bez konwersji algorytm nie ma jak optymalizować i pali kasę losowo.

Dodałem:

- `trackPurchase()` w `gtag.ts` — strzela `gtag('event', 'purchase')` do GA4 zawsze, plus `gtag('event', 'conversion', { send_to: 'AW-XXX/LABEL' })` do Google Ads gdy oba env vars są ustawione przy build-time.
- Wywołanie w `BookProgressShell` w tym samym `useEffect` co PostHog `payment_success`.
- Idempotencja: `transaction_id: orderId` — refresh strony sukcesu nie produkuje duplikatów po stronie Google'a.
- `setAnalyticsConsent` rozszerzony — teraz flipuje też `ad_storage` / `ad_user_data` / `ad_personalization` (poprzednio tylko `analytics_storage`, co dla Google Ads modelu konwersji robiło różnicę w atrybucji nawet dla zaakceptowanych userów).

### 5. Bonus: gclid + UTM capture

Stworzyłem `src/lib/attribution.ts`. Snapshot `gclid`/`gbraid`/`wbraid`/`fbclid`/`msclkid`/`utm_*` na pierwszej wizyt → localStorage → super properties PostHog. Survive'uje Stripe round-trip który zabija `document.referrer`. First-touch attribution (subsequent visits nie nadpisują).

Po `payment_success` event do PostHog dostaje attribution w payload — funnel reports można splitować po kampanii.

## Architektoniczna obserwacja

Server-side analytics (edge middleware → Convex `pageViews`) od 21 maja był jedynym źródłem prawdy o ruchu w 30 dni — bo GA4 z Consent Mode v2 default-deny widzi tylko consenting users, a PostHog z `optOutCapturingByDefault: true` to samo. Mobile-PL accept rate cookies ~20-40%, więc GA4 pokazuje 25-40% rzeczywistego ruchu. To by tłumaczyło "350 → kilka" nawet bez całej reszty problemów.

Wniosek: Consent Mode v2 to legalny obowiązek, ale dla decyzji biznesowych trzeba mieć drugi obraz (server-side beacon). Mamy. Tylko trzeba pamiętać żeby tam patrzeć zamiast w GA4.

## Co dalej

- Cezary musi ustawić env vars w Vercel przed odpaleniem kampanii:
  - `VITE_GOOGLE_ADS_ID` = `AW-XXXXX...`
  - `VITE_GOOGLE_ADS_PURCHASE_LABEL` = label conversion action
  - `VITE_BOOK_VALUE_PLN` = wartość (np. `39`) jeśli chce value-based bidding
- Po deployu sprawdzić Google Ads → Tools → Conversions → status "Receiving conversions"
- Followup: server-side conversion API (Stripe webhook → Google Ads Enhanced Conversions API) — backup gdy ad-blockery utną gtag. Większa robota, osobny PR.
