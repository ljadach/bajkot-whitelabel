# 2026-04-27 — Stripe one-shot + admin sandbox

## Decyzja modelu

Zamykam pytanie z 2026-04-23. Wybrane: **one-shot per ksiazka**. Aitutorc-owy model subscription byl zawyzony do potrzeb bajkot — jedna ksiazka = jedna platnosc. Schemat `bookOrders` juz mial `paymentStatus` + `stripeSessionId`, czyli kod sam podpowiadal kierunek.

Konsekwencje:

- Tabela `subscriptions` wyleciala ze schemy. Razem z nia: `convex/lib/billing.ts` (subscription helpers), wszystkie funkcje subscription state w `convex/billing.ts`, `createCustomerPortalSession` w `convex/stripe.ts`. Customer Portal zbedny przy one-shot (nie ma czego anulowac).
- `STRIPE_PRO_PRICE_ID` → `STRIPE_BOOK_PRICE_ID`. Cena ma byc `one-time` w Stripe, nie recurring.
- Webhook handler odchudzony do jednego case'u: `checkout.session.completed` z `mode=payment, payment_status=paid` → `markBookOrderPaid` patch na `bookOrders`.

## Backend

`convex/stripe.ts`:

- `createCheckoutSession({ bookOrderId, returnPath? })` — public action. Sprawdza ownership (`order.clerkUserId === identity.subject`) i ze nie jest juz zaplacone. Zapisuje `stripeSessionId` na bookOrder przed zwroceniem URL (zeby pollowac status nawet bez webhooka, jesli kiedys bedzie potrzeba).
- `verifyWebhookEvent({ payload, signature })` — internal action. Tylko `checkout.session.completed` w trybie `payment`. Pobiera `bookOrderId` z `metadata.bookOrderId` (fallback `client_reference_id`).

`convex/billing.ts` zredukowane do 4 funkcji: `getBookOrderForCheckout` (internal Q), `attachStripeSessionId` (internal M), `markBookOrderPaid` (internal M, idempotent — sprawdza czy juz `completed`), `getBookOrderPaymentStatus` (public Q dla frontendu, gateowane przez ownership).

## Admin sandbox

`/admin/stripe` (`src/admin/pages/AdminStripe.tsx`) ma trzy sekcje:

1. **Konfiguracja** — checklista 4 env varow (`STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_BOOK_PRICE_ID`, `APP_URL`). Czerwone/zielone kropki, bez ujawniania wartosci. Backend: `api.admin.stripe.stripeConfigStatus`.
2. **Testowe zamowienia** — admin tworzy fake bookOrder (problemId: `'stripe-test'`, status: `'paused'` zeby pipeline nie ruszyl), klika **Otworz Checkout** → redirect na Stripe → po zaplacie wraca na `/admin/stripe` → status w tabelce zmienia sie na `completed` na zywo (Convex reactive query).
3. **Webhook smoke test** — instrukcja `stripe listen` + test card numer.

`convex/admin/stripe.ts`: `createTestOrder`, `listTestOrders` (filtruje `problemId === 'stripe-test'` zeby nie zasmiecac listy real orderow), `deleteTestOrder` (sprzata po sobie), `stripeConfigStatus`. Wszystkie pod `assertAdmin`.

## Trade-offs

- Admin sandbox tworzy `bookOrders` w prawdziwej tabeli (status `paused`). Mozna by zrobic osobna `bookOrdersTest` ale to over-engineering — `paused` nie odpalafa pipelina, a filtrowanie po `problemId === 'stripe-test'` izoluje testy w UI. Trzeba pamietac, ze admin batch / zwykly user nie zobaczy tych orderow (nie sa jego, plus odfiltrujemy w batch widoku jesli zacznie przeszkadzac).
- `createCheckoutSession` wymaga `identity.email`, ale jesli go nie ma — Checkout sam zapyta. Nie blokujemy.
- Webhook ignoruje `payment_status !== 'paid'` (np. `unpaid`, `no_payment_required`). Jesli kiedys zaczniemy uzywac `automatic_tax` z reverse charge i pojawi sie `no_payment_required` — trzeba bedzie wlaczyc.
- Frontend bookflow (UI dla zwyklego uzytkownika z buttonem "Zaplac" na `/book/:id/result`) nie jest dotykany. Dzisiaj zalozenie: po dostarczeniu PDF user widzi gate platnosci. To odlozone — sandbox wystarczy do walidacji integracji.

## Co dalej

1. Admin: ustawic env vary w Convex (`stripeConfigStatus` ma kropeczki).
2. Lokalnie: `stripe listen --forward-to <dep>.convex.site/stripe/webhook`.
3. Smoke test: stworz testowe zamowienie → Otworz Checkout → karta 4242 → wroc na `/admin/stripe` → potwierdz `completed`.
4. Dopiero po zielonym smoke teście: frontend gate na `/book/:id/result` (button "Zaplac za PDF") + kasacja referencji `docs/stripe-import-from-aitutorc/` (zostalo do skopiowania, juz wzieli swoje).
