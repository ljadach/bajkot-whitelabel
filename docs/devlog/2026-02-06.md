# 2026-02-06 — Email deliverability fix

## Problem

Maile z Clerka (weryfikacja, logowanie) trafiały do spamu. Domena `aitutoro.com` miała 31 dni — zero reputacji mailowej. DKIM od Clerka (SendGrid) był jedynym skonfigurowanym mechanizmem. Brakowało SPF, DMARC i MX.

## Co zrobiliśmy

### DNS records dodane na Vercelu (CLI `vercel dns add`)

| Typ | Name | Value | Cel |
|-----|------|-------|-----|
| TXT | `@` | `v=spf1 include:_spf.clerk.services include:sendgrid.net include:spf.improvmx.com ~all` | SPF — autoryzacja serwerów do wysyłki |
| TXT | `_dmarc` | `v=DMARC1; p=quarantine; pct=100; rua=mailto:cezdmo@gmail.com;` | DMARC — polityka obsługi nieautoryzowanych maili |
| MX | `@` | `10 mx1.improvmx.com` | Odbiór maili na domenie |
| MX | `@` | `20 mx2.improvmx.com` | Fallback MX |

### ImprovMX (free tier)

Forwarding `notifications@aitutoro.com` → `cezdmo@gmail.com`. Dzięki temu domena ma realny mailbox za adresem "from" Clerka, co poprawia wiarygodność u providerów (Gmail, Outlook sprawdzają czy za adresem nadawcy stoi skrzynka).

Konto: improvmx.com, domena `aitutoro.com`.

### Istniejące rekordy Clerk (bez zmian)

| Typ | Name | Value |
|-----|------|-------|
| CNAME | `clk._domainkey` | `dkim1.kvcakmcs1h8k.clerk.services.` |
| CNAME | `clk2._domainkey` | `dkim2.kvcakmcs1h8k.clerk.services.` |
| CNAME | `clkmail` | `mail.kvcakmcs1h8k.clerk.services.` |
| CNAME | `accounts` | `accounts.clerk.services.` |
| CNAME | `clerk` | `frontend-api.clerk.services.` |

## Pełny stan DNS aitutoro.com

```
SPF:   v=spf1 include:_spf.clerk.services include:sendgrid.net include:spf.improvmx.com ~all
DMARC: v=DMARC1; p=quarantine; pct=100; rua=mailto:cezdmo@gmail.com;
DKIM:  Clerk/SendGrid (clk._domainkey, clk2._domainkey)
```

# 2026-02-06 — Admin Content Processing Pipeline

## Kontekst

Lekcje w AITutor to tekst. Chcemy wzbogacić o wideo — nagrania screenu jak ktoś klika po narzędziu AI. Pipeline: surowe filmy z Google Drive → LLM analizuje klatki → JSON z segmentami (co, kiedy, metadane) → human review → wersjonowany korpus wiedzy → LLM dobiera pasujące fragmenty do lekcji.

## Architektura

Decyzja: **lazy-loaded `/admin/*` route** w tym samym SPA. Zero kodu admina w bundlu regular usera. Rozważane alternatywy: osobna Vite app (overkill), feature flags bez lazy loading (admin code w bundlu wszystkich), zewnętrzne narzędzie (Retool — brak reużycia Convex).

### Backend (`convex/admin/`)

4 nowe tabele w schema.ts: `adminConfig`, `pipelineVideos`, `videoSegments`, `knowledgeCorpora`.

4 moduły backend functions:
- `config.ts` — CRUD admin settings (Google Drive URL, model, parametry)
- `videos.ts` — lista filmów, dodawanie, usuwanie, processing stub
- `segments.ts` — CRUD segmentów, toggle on/off, tagowanie, bulk operations
- `corpus.ts` — merge segmentów w wersjonowany korpus z filtrowaniem po tagach

Każda funkcja ma `assertAdmin(ctx)` na starcie. `processVideo` i `insertSegments`/`updateStatus` jako `internalMutation` — niedostępne z frontendu.

### Frontend (`src/admin/`)

- `AdminLayout.tsx` — lazy entry point, sidebar nav, sub-router, guard `isAdmin`
- 5 stron: Dashboard (karty), Config, VideoList, SegmentEditor, CorpusEditor

Segment Editor to review board: lista segmentów z inline preview, toggle on/off, tagi (redacted/check_again/unsure/verified/highlight), filtry, bulk actions. Double-click na opis otwiera inline edit.

Corpus Editor: wybierz filmy, filtruj po tagach (include/exclude), "Sklej" → nowy wersjonowany korpus z datą. Historia wersji z podglądem contentu.

### Bezpieczeństwo

Dwa niezależne audyty (silent failure + security review):
- Auth coverage: 100% — 22/22 backend functions chronione
- Fixnięto: fire-and-forget mutations (delete, toggle, tag) → try/catch + toast
- Fixnięto: brak confirm dialog na delete (cascade!) → window.confirm
- Fixnięto: JSON.parse crash w preview metadata → try/catch fallback
- Fixnięto: clipboard copy bez await → async + catch
- Dodano: walidacja tagów (alphanumeric, max 50 chars) i opisów (max 5000 chars)

### E2E testy

Playwright: `e2e/tests/04-admin-pipeline.spec.ts` — 13 testów pokrywających: access denial, layout/nav, config save/load, video CRUD, processing stub, segment toggle/tag, corpus merge, sidebar navigation.

## Decyzje

- **processVideo to stub** — generuje mock segmenty. Prawdziwa integracja z LLM + video frames wymaga osobnego etapu. Celowe — frontend jest gotowy, backend processing do wymiany.
- **Brak i18n** — admin-only tool, angielski wystarczy. Nie puchniemy translation keys.
- **Flat tag model** — tagi to plain strings bez hierarchii. Wystarczające na start, można rozbudować jeśli potrzeba.

# 2026-02-06 — Real video processing pipeline (Gemini native video)

## Co zrobiono

Zamieniono stub `processVideo` na prawdziwą integrację z Gemini File API + native video input.

### Backend

**`convex/lib/videoProcessing.ts`** — nowy moduł:
- Download z Google Drive → upload do Gemini File API → analiza chunkami z overlapem
- Gemini REST API bezpośrednio przez `fetch()` — `@ai-sdk/google` crashuje tsc (overload resolution bug)
- Chunking: wideo dzielone na odcinki max N minut z M sekund overlapa (konfigurowalne)
- Merge: deduplikacja segmentów w strefach overlapa (threshold 0.5s), re-indeksowanie ID
- Pełna observability: `startActiveObservation`, `storeLlmLog` per chunk

**`convex/lib/googleDrive.ts`** — sync helpers:
- `listVideosInFolder()` — Drive API v3, filtrowanie `mimeType contains 'video/'`
- `compareWithExisting()` — hash matching (`simpleHash(fileName + ':' + durationOrSize)`)
- Zwraca `SyncResult[]` z flagą `isNew`

**`convex/admin/videos.ts`** — nowe endpointy:
- `syncFromGoogleDrive` action — lista plików z folderu GDrive vs istniejące filmy
- `bulkAddFromSync` action — masowe dodanie nowych filmów do pipeline
- `getById` query — potrzebne przez `processVideo`
- `processVideo` action — prawdziwa implementacja (download → Gemini → parse → store)

**Schema**: dodano `googleDriveFileId`, `toolDetected`, `uiVersion` do `pipelineVideos`.

**Prompty**: `VideoSegmentExtractionSystem` + `VideoSegmentExtractionUser` w `prompts.ts` z przykładami segmentów z prawdziwych danych.

### Frontend

**`VideoList.tsx`** — przycisk "Sync Google Drive":
- Wyciąga listę plików z GDrive, porównuje z istniejącymi
- Panel z checkboxami: new/exists status, rozmiar, czas trwania
- Pre-selektuje nowe pliki, "Add Selected" dodaje do pipeline
- Nowa kolumna "Tool" w tabeli — detected AI tool + UI version

**`AdminConfig.tsx`** — nowe pola konfiguracji:
- `processing_chunk_minutes` — rozmiar chunka (domyślnie 5 min)
- `processing_overlap_seconds` — overlap między chunkami (domyślnie 30s)
- Fix: nazwy kluczy zsynchronizowane z backendem (`min_segment_duration` zamiast `segment_min_duration`)

### TypeScript crash fix

`@ai-sdk/google@3` + `ai@5` ma niekompatybilne typy (SharedV3 vs SharedV2 ProviderOptions). Na TS 5.7.3 tsc crashował z "Debug Failure. No error for last overload signature" — bug w resolverze overloadów. Upgrade do TS 5.9.3 naprawia crash. Dodano `as any` na `google()` model w `quickTipAi.ts` żeby wyeliminować type errors (pre-existing, ale teraz widoczne).

## Decyzje

- **Gemini REST API zamiast `@ai-sdk/google`** — SDK crashuje TypeScript compiler. Direct fetch działa identycznie, bez dependency na problematyczne typy.
- **TypeScript 5.7.3 → 5.9.3** — fix na tsc crash. Nie powinno nic zepsuć (patch release).
- **Chunking w backendzie, nie frontendzie** — action robi download + upload + chunking. Frontend tylko kickuje process i czeka na status.
- **`as any` na google() w quickTipAi.ts** — version mismatch `@ai-sdk/google@3` vs `ai@5`. Upgrade SDK byłby idealny, ale ryzykowne bez pełnego testu.

# 2026-02-06 — Production hardening + Corpus→Lesson integration

## Production hardening

**`convex/lib/adminGuards.ts`** — nowy moduł z 4 mechanizmami:

1. **Rate limiting admin endpoints** — `admin_action: 60/min` (reużycie sliding window z `rateLimiter.ts`). Generyczny, nie per-endpoint — wystarczy na start.

2. **Audit log** — nowa tabela `adminAuditLog` z `actor`, `action`, `target`, `details` (JSON), `timestamp`. Wrapper `auditLog()` wywoływany w:
   - `config.set` — loguje stary i nowy value
   - `video.add` / `video.remove` — loguje fileName, usunięte segmenty
   - `corpus.merge` / `corpus.remove` — loguje version, segment count

3. **Bulk ops limit** — `assertBulkLimit(ids, 200)` dodany do `bulkToggle`, `bulkSetTags`, `bulkAddTag`, `bulkAddFromSync`.

4. **Config validation** — `validateConfigValue()` w `config.set`:
   - `google_drive_url` → must contain `drive.google.com`
   - `llm_model` → must start with `gemini-`
   - Numeric fields → must be positive numbers

## Corpus→Lesson integration

Podejście: wstrzyknięcie korpusu wideo jako dodatkowy kontekst do generowania handbooków (lekcji). Nie modyfikuję schematu `planFull` — referencje do segmentów wideo naturalnie płyną w markdown content.

**Zmiany:**
- `HandbookSystem` prompt — dodane guideline o referencjach wideo ("As shown in the demo at 2:15...")
- `HandbookUser` prompt — nowy placeholder `{{VIDEO_CORPUS}}` z corpus content
- `courseAi.ts: generateHandbookInternal` — ładuje aktywny korpus z admin config (`active_corpus_id`), wstrzykuje do promptu. Jeśli brak — kontynuuje normalnie.
- `AdminConfig.tsx` — nowe pole "Active Corpus ID" do konfiguracji

**Flow:**
1. Admin buduje korpus w Corpus Editor
2. Admin wkleja corpus ID do Pipeline Config → `active_corpus_id`
3. Przy generowaniu lekcji, `generateHandbookInternal` ładuje korpus i dodaje jako kontekst
4. LLM naturalnie referencjonuje segmenty w treści rozdziałów

## Decyzje

- **Audit log bez rate limit enforcement** — audit log jest pure append. Rate limit dodany do configa, ale nie wpiąłem `checkAdminRateLimit()` do każdego handlera — admin to max 1-2 osoby, bulk limit wystarczy. Można dodać jeśli potrzeba.
- **Corpus injection opcjonalne** — brak `active_corpus_id` = normalne generowanie bez wideo. Zero breaking changes.
- **Corpus ID as config string** — nie waliduje czy ID istnieje w momencie zapisu. Walidacja leniwa (przy ładowaniu). Prostsze, mniej edge cases.

# 2026-02-06 — Audyt bezpieczeństwa sekcji admin

## Scope

Pełny przegląd `/admin/*` — frontend routing, backend endpoints, auth, CORS, input validation, audit trail.

## Wynik ogólny

Fundament solidny. Clerk JWT + `assertAdmin()` na 22/22 endpointach. Brak luk w autoryzacji. Problemy dotyczą production hardening — brak rate limiting, audit logu, i wildcard CORS.

## Naprawione

### CORS wildcard → explicit origin (`convex/streaming.ts`)

Było `Access-Control-Allow-Origin: *` na endpoincie streamingowym. Dowolna strona mogła robić authenticated requests. Zamienione na `process.env.ALLOWED_ORIGIN` z fallbackiem na `http://localhost:5173`. W produkcji ustawić env var `ALLOWED_ORIGIN` w Convex Dashboard.

## Otwarte znaleziska

### 🟡 Brak rate limitu na admin endpoints

Rate limiting działa tylko dla user-facing ops (`llm_call: 30/5min`, `profile_update: 100/min`). Admin endpoints mają zero throttlingu. Skompromitowane konto admina = nieograniczone wywołania LLM i bulk operacje.

### 🟡 Brak audit logu

Admin może zmieniać config, usuwać wideo, modyfikować segmenty bez historii zmian. `updatedBy` w `adminConfig` to jedyne co mamy — brak timestampów zmian ani diffów. Debugging "kto co kiedy zmienił" = niemożliwy.

### 🟡 Brak limitów na bulk operations

`bulkToggle()`, `bulkSetTags()`, `bulkAddTag()` przyjmują tablice ID bez limitu rozmiaru. Dodać max ~200 elementów per request.

### 🟡 Brak walidacji wartości config

Admin może ustawić `llm_model` na dowolny string. System po cichu failuje na OpenRouter. Potrzebna walidacja enum znanych modeli.

### 🟢 Co jest OK

- Auth coverage 100% — `assertAdmin()` na każdym public endpoincie
- Internal mutations (`updateStatus`, `insertSegments`) prawidłowo jako `internalMutation`
- Brak `dangerouslySetInnerHTML` w admin — React domyślnie escapuje
- Tag validation: regex + max 50 chars
- Description validation: max 5000 chars server-side
- `.env` nie jest w gicie

## TODO

- [ ] Rate limiting na admin endpoints (sliding window jak user-facing)
- [ ] Audit log table: `adminAuditLog(actor, action, target, diff, timestamp)`
- [ ] Max size na bulk ops (200 elementów)
- [ ] Walidacja config values (enum modeli, format URL)
- [ ] Ustawić `ALLOWED_ORIGIN` env var na produkcji w Convex Dashboard

# 2026-02-06 — Cloudflare Stream integration + segment preview player

## Kontekst

Wideo serwowane z Google Drive iframe to ślepa uliczka: brak kontroli nad start/end time, `#t=` fragment unreliable, brak endTime w ogóle. Potrzebujemy docelowego rozwiązania na serwowanie fragmentów wideo z precyzyjnymi granicami czasowymi — zarówno w admin preview jak i docelowo w kursach.

## Analiza kosztów i wybór platformy

Porównanie: Cloudflare Stream vs Mux vs Bunny Stream vs S3+CloudFront. Scenariusz: 100 użytkowników, ~5 min realnego wideo na osobę tygodniowo (krótkie klipy osadzone w materiałach).

| Platforma | Koszt/mies | Uwagi |
|-----------|-----------|-------|
| Cloudflare Stream | ~$6 | $5 storage + $1 encoding, $0 egress |
| Bunny Stream | ~$1-2 | Najtańsze, ale mniej dojrzałe API |
| Mux | ~$8-12 | Najlepsze DX, najdroższe |
| S3+CloudFront | ~$2-5 | Brak startTime/endTime w playerze |

**Decyzja: Cloudflare Stream.** Zero egress fees (CF ma CDN w cenie), natywne `startTime`/`endTime` w iframe playerze, prosty API, wystarczające na naszą skalę.

## Backend

### `convex/lib/cloudflareStream.ts` (nowy)

Klient CF Stream API:
- `uploadVideo()` — direct creator upload, FormData + Blob (max 200MB)
- `waitForReady()` — polling co 5s, max 5 min, rzuca na error/timeout
- `getVideoStatus()`, `deleteVideo()` — CRUD
- `getIframeUrl()` — buduje URL z startTime/endTime/loop/autoplay/muted
- `getHlsUrl()` — manifest HLS do ewentualnego użycia z hls.js

Convex runtime nie ma Node.js `Buffer`. Wszystkie operacje binarne przez `Uint8Array` + `Blob`. Custom `concatUint8Arrays()` helper zamiast `Buffer.concat()`.

### `convex/admin/videos.ts` — rozszerzenia

- `processVideo` — po analizie Gemini, download wideo z GDrive i upload do CF Stream. Non-fatal: jeśli CF upload padnie, segmenty i tak się zapisują.
- `uploadToCloudflare` — standalone action do uploadu istniejącego wideo
- `_backfillCloudflare` — internal action do masowego backfillu (wywoływane z CLI)
- Schema: `cloudflareStreamUid: v.optional(v.string())` w `pipelineVideos`

### `convex/lib/videoProcessing.ts` — fixy

- `Buffer.from()` → `new Uint8Array()` (Convex runtime)
- `Buffer.concat()` → `concatUint8Arrays()` custom helper
- Dodana `repairTruncatedJson()` — Gemini czasem ucina response, fallback chain: parse → extract → repair extracted → repair raw

### `convex/lib/googleDrive.ts`

- Export `simpleHash()` i `SyncResult` (były zduplikowane w videos.ts)

## Frontend

### `src/admin/components/SegmentVideoPlayer.tsx` (nowy)

Dedykowany komponent playera. Tylko CF Stream, zero GDrive fallback:
- Props: `cloudflareStreamUid`, `cloudflareCustomerSubdomain`, `startSeconds`, `endSeconds`
- Iframe z `autoplay=true`, `muted=true`, `loop=true` + startTime/endTime
- Fallback: "Not uploaded to Cloudflare Stream" (zamiast GDrive)

### `src/admin/pages/SegmentEditor.tsx`

- Zamiana inline GDrive iframe na `<SegmentVideoPlayer>`
- `key={activePreview._id}` — wymusza remount iframe przy zmianie segmentu. Bez tego React reużywał DOM element i przeglądarka ignorowała zmianę `src`.
- Fix floating point duration: `Math.round((end - start) * 10) / 10`

## Env vars

- `CLOUDFLARE_ACCOUNT_ID` + `CLOUDFLARE_STREAM_API_TOKEN` — Convex env (backend)
- `VITE_CLOUDFLARE_CUSTOMER_SUBDOMAIN` — `.env.local` (frontend, potrzebny do budowy iframe URL)

## Bugi po drodze

1. **`Buffer is not defined`** — Convex runtime ≠ Node.js. Zamiana na Uint8Array + Blob.
2. **SyncResult validator mismatch** — returns validator brakowało `id` i `mimeType` z interfejsu.
3. **JSON parse error** — Gemini ucina response. Dodana repair chain.
4. **Iframe nie reaguje na zmianę segmentu** — React reużywa iframe DOM, przeglądarka nie przeładowuje na zmianę `src`. Fix: `key={segmentId}`.

## Decyzje

- **Tylko CF Stream, zero GDrive fallback** — docelowe rozwiązanie. Wideo bez CF upload pokazuje "Not uploaded" zamiast degraded experience.
- **Non-fatal CF upload w pipeline** — jeśli CF padnie, segmenty z Gemini i tak się zapisują. CF upload można zrobić retroaktywnie backfillem.
- **Iframe zamiast hls.js** — prostsze, CF iframe ma wbudowane kontrolki, startTime/endTime natywnie. hls.js byłby potrzebny gdybyśmy chcieli custom UI.
