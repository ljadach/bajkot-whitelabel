## Dokumentacja modelu danych

Stworzyliśmy dwa dokumenty techniczne:

### `docs/data-model.md`
Pragmatyczna analiza schematu Convex. Kluczowe obserwacje:

1. **XML jako canonical source of truth** - nieoczywista, ale mądra decyzja dla LLM workflows
2. **JSON-in-strings** - `planOutline`, `planFull`, `profileState` to stringified JSON (tracisz type safety)
3. **15 tabel** w 4 domenach: core flow, gamifikacja, progress tracking, organizacje
4. **Brak retention policy** dla logów - `backendLogs`, `activityLog` rosną bez limitu
5. **`google-nano-banana`** - hardcoded mock model name, tech debt

### `docs/migration-strategy.md`
Głęboka analiza strategii migracji w Convex:

1. **Convex ≠ SQL** - brak tradycyjnych migracji, schema jest deklaratywna
2. **Expand-Contract pattern** - jedyny bezpieczny wzorzec dla breaking changes
3. **Fazy:** EXPAND → MIGRATE → DUAL-WRITE → VERIFY → CONTRACT
4. **Anti-patterns:** Big bang migration, schema change przed backfill, usuwanie indexu przed dodaniem nowego

## Decyzja: czy zaorać dane?

**Kontekst:** Aplikacja w fazie wczesnego developmentu. Dane w bazie to głównie:
- Testowe profile z E2E testów
- Debug logi z developmentu
- Ewentualnie kilka profili z demo

**Argumenty za zaoraniem:**

1. Migracja sessionId→clerkUserId staje się trywialna (usuwasz pole, nie backfillujesz)
2. JSON-in-strings można naprawić od razu (nowy schema, czyste dane)
3. Legacy `duration` field - nie trzeba weryfikować czy jest używane
4. `google-nano-banana` - możesz usunąć lub zmienić na właściwy model
5. Czysta baza = mniej edge cases w kodzie

**Argumenty przeciw:**

1. Jeśli masz prawdziwych użytkowników - utrata ich danych
2. Musisz przerobić cały kod na nowy schema jednocześnie
3. Brak rollback - jak coś pójdzie źle, nie wrócisz do starego

**Rekomendacja:**

Jeśli **<10 realnych użytkowników** (nie testowych) → **ZAORAĆ**.

Procedura:
1. Export danych z dashboard (backup)
2. Usuń wszystkie dokumenty z tabel (lub usuń deployment i stwórz nowy)
3. Zaktualizuj schema:
   - Usuń `sessionId` z `llmLogs`
   - Usuń `duration` z `trainingOutline`
   - Zdecyduj o `planOutline`/`planFull` - typed objects lub zostawić
4. Deploy
5. Sprawdź że aplikacja startuje
6. Uruchom E2E testy

**Nie zaorywać:**
- `google-nano-banana` - zostaw, to placeholder na przyszłość
- JSON-in-strings - można zmigrować expand-contract później
- `backendLogs`/`activityLog` retention - dodaj cleanup cron, nie wymaga migracji

## Streamlining verification flow

### Problem

Happy path miał za dużo kroków. Po submicie prompta na /verification user widział wyniki i musiał kliknąć Continue.

### Rozwiązanie

**Linear flow (happy path):**
- Chat → Verification (submit) → **auto-navigate** → Summary
- Brak ekranu z wynikami weryfikacji (są potem na Summary)

**Direct link (/verification):**
- Jeśli user ma verification w DB → pokazuje wyniki + ContinueBar
- Może iść dalej lub zregenerować

### Zmiany

```typescript

void navigate('/summary');  // auto-navigate po zapisie
```

```typescript

  await this.submitPrompt(prompt);
  await this.page.waitForURL(/\/summary/, { timeout: ... });
}
```

## Fix step blocking redirects

### Problem

Komunikat "Step blocked" kierował do złego kroku. Np. /summary bez ukończenia chat → kierował do /verification zamiast /chat.

### Przyczyna

`useStepNavigation.ts` używał `profileXml.length > 100` jako proxy dla "chat ukończony". Ale profileXml może istnieć nawet przy nieukończonym intake (user odpowiedział na kilka pytań, ale LLM nie zwrócił `complete: true`).

### Rozwiązanie

Zmiana na `intakeComplete` flag (ustawianą przez LLM):

```typescript
// Stare
case 'verification':
  return !!profile.profileXml && profile.profileXml.length > 100;

// Nowe
case 'verification':
  return !!profile.intakeComplete;
```

### Eligibility matrix (po zmianach)

| Step | Wymaga |
|------|--------|
| `/chat` | (zawsze dostępny) |
| `/verification` | `intakeComplete: true` |
| `/summary` | `skillVerification` |
| `/plan` | `assessmentReport` |
| `/complete` | `planOutline` |
