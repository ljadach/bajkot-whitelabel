# 2026-05-12 — Security audit + fixes C1/C2/C3/H1

## Skąd to się wzięło

Audyt na branchu `security-audit-2026-05-12` (PR #43) namierzył 3 krytyczne i 3 wysokie dziury w landing flow + auth. Plan: zamknąć cztery najgrubsze (C1, C2, C3, H1) w jednym podejściu, bo siedzą w tych samych plikach.

## C1 — `skipStripe` / `fastImage` / `skipQaReviews` w public actions

Frontend domyślnie wysyłał `skipStripe: true`. Każdy mógł odpalić `startOrder` / `startLandingOrder` z tym i odebrać PDF bez płacenia. `isPaid()` traktowało `skipStripe === true` jako "zapłacone".

Fix:

- Z `startOrder` i `startLandingOrder` poleciały wszystkie trzy flagi z validatorów args. Convex odrzuci każde wywołanie, które jeszcze próbuje je przekazać.
- `isPaid()` patrzy już tylko na `paymentStatus === 'completed'`. Webhook Stripe to jedyna ścieżka która to flipuje (plus CLI/admin batch, które ustawiają to bezpośrednio przy insert).
- `presignForOrder` — to samo, R2 download wymaga teraz `paymentStatus === 'completed'`.
- `OrderPreview.tsx` — diagnostyczny panel checkboxów (skipStripe / skipQa / fastImage) zniknął. `AuthOrderFlow` i `LandingOrderFlow` przestały zarządzać tym stanem, zniknął "admin shortcut" w preview-continue.
- `convex/cli.ts:createOrder` — zamiast `skipStripe: true` ustawia `paymentStatus: 'completed' as const` przy insert. Test orders są od razu "zapłacone", nie polegają na osobnym flagu.
- `cli:setUnpaid` — czyści tylko `paymentStatus: 'pending'`.

Schema zostawia `skipStripe` / `fastImage` jako `v.optional(v.boolean())` — żeby legacy dane się walidowały. `fastImage` i `skipQaReviews` dalej żyją w `bookAgents.ts` jako tryby pracy (ustawiane tylko z internal paths: CLI + admin batch).

## C2 — Per-order tokeny dla landing

Wszystkie landing orders chodziły pod `clerkUserId: "landing-user"`. `assertLandingOrder` tylko sprawdzał, czy `clerkUserId` to ten sentinel. Każdy z URL-em zamówienia mógł odczytać dane dziecka, zagłosować na styl, dodać dedykację. Convex ID nie miało być autoryzacją — a było.

Plan: capability token per order. Generowany w `startLandingOrder`, zwracany raz, hash trzymany w DB.

Backend:

- `convex/lib/landingToken.ts` — 32-bajtowy random (`crypto.getRandomValues`) → base64url. Hash przez Web Crypto `subtle.digest('SHA-256', ...)` → hex. `timingSafeEqual` przez XOR loop, bo gołe `===` ma timing channel (tu nieistotny dla SHA-256 hashy, ale defense-in-depth).
- `schema.ts` — `accessTokenHash: v.optional(v.string())` na `bookOrders`.
- `assertLandingOrder(ctx, orderId, accessToken)` — fail-closed jeśli brak `accessTokenHash` (legacy data) albo token nie pasuje.
- Wszystkie public landing entry-pointy w `bookPipeline.ts` (`getLandingOrderProgress`, `getLandingOrderEvents`, `getLandingStyleVoteImages`, `submitLandingStyleVote`, `submitLandingParentDedication`, `skipLandingParentDedication`, `getLandingOrderPreview`, `getLandingDownloadUrl`, `getLandingPrintThanksOrder`) — dostały `accessToken: v.string()` w args.
- `resolveLandingR2DownloadUrl` (action) i `createLandingCheckoutSession` w `stripe.ts` weryfikują przez `internal.bookPipeline.verifyLandingTokenInternal` (action nie może ssać Convex DB bezpośrednio).
- `startLandingOrder` zwraca `{ orderId, accessToken }` zamiast samego `orderId`.

Frontend:

- `src/hooks/useLandingOrderToken.ts` — `saveLandingOrderToken(orderId, token)` / `getLandingOrderToken(orderId)`. localStorage key `bajkot_landing_order_tokens`, mapa `orderId → token`.
- `LandingOrderFlow.tsx` — po `startLandingOrder` woła `saveLandingOrderToken`.
- `BookProgressShell.tsx` — w landing flow czyta token z localStorage, składa args przez `buildArgs`. Jeśli token brak (inny browser, wyczyszczony storage) — pokazuje `not found` zamiast wisieć na spinnerze.
- `LandingBookResult.tsx`, `PrintThanks.tsx`, `useResolvedR2Url.ts` — wszystkie pobierają token z hooka i dołączają do wywołań.

Konsekwencja H3 (Stripe landing checkout fail-open) — `createLandingCheckoutSession` przestało polegać na env `LANDING_ACCESS_TOKEN` i też używa per-order tokena. Ten audit point zamyka się przy okazji.

## C3 — Landing intake gate + rate limit

`startLandingOrder` miał token check zakomentowany, plus zero rate-limitu. Każdy kto znalazł endpoint mógł odpalać LLM pipeline w pętli.

- Re-enable gate: `LANDING_ACCESS_TOKEN` znów wymagany. **Fail-closed w prod**: jeśli env var nie ustawiony i deployment to `wonderful-egret` (prod), action rzuca `'Landing intake disabled'`. W dev (gdy env brak) — action przepuszcza, żeby smoke testy się nie zablokowały.
- Rate limit: nowy typ `landing_start` w `RATE_LIMIT_CONFIG` (60 calls / godz, globalnie). Klucz to constant `LANDING_RATE_LIMIT_KEY = '__landing_global__'` — wszyscy anonimowi callers dzielą jeden bucket. `checkAndRecordLandingStart` w `rateLimitMutation.ts`. Token gate + rate limit wywoływane na samej górze handlera, przed sanitize i LLM guards.

Globalny cap jest świadomie konserwatywny, bo każda generacja to realny koszt LLM + image gen. Jak skala wzrośnie — przejdzie się na per-IP, ale wtedy będzie identity (Stripe gate), więc anonymous quota zniknie.

## H1 — Dependency upgrades

`npm audit --omit=dev` raportował 19 prod vulns (5 critical, 7 high, 7 moderate). Spectacular: `@clerk/shared` middleware bypass (critical, CVSS 9.1), `protobufjs` RCE przez OpenTelemetry/Langfuse (critical), `vite` fs deny bypass.

`npm audit fix --omit=dev` zamknął wszystkie criticals + highs:

- `@clerk/clerk-react` → 5.61.6
- `@clerk/react-router` → 2.4.13
- `@clerk/backend` → 2.33.3
- `@clerk/shared` → 3.47.5 (poza vulnerable range)
- `protobufjs` → 7.5.8 / 8.0.1 (zależnie od ścieżki)
- `vite` → 7.3.3

Zostały 3 moderate w `ajv` (ReDoS), tranzytywnie przez `@vercel/static-config` → `@vercel/react-router`. `fixAvailable: false`. Akceptowalne na ten moment: `@vercel/react-router` używany tylko przy build/deploy, nie w runtime, więc atakujący nie ma jak strzelić w to dev-time-only RegExp.

## Trade-offy

- Token w localStorage = jeśli user wyczyści storage albo wejdzie z innego urządzenia, "traci" zamówienie. Akceptujemy: landing flow to one-shot, parent zostaje w tej samej sesji do końca. Pod payment unlock i wysłanie maila wyciągnie się token osobnym mechanizmem (np. magic link).
- `accessTokenHash` jest `v.optional()` w schemie, ale `assertLandingOrder` fail-closes jak nie ma. Legacy landing orders (sprzed dziś) odpadają z czytania — pre-launch, więc to tylko orders testowe, nie real revenue.
- Schema dalej trzyma `skipStripe` / `fastImage` jako optional fields. Cleanup later, ale po `isPaid` zmianie pole `skipStripe` jest martwe — nic go nie czyta.
